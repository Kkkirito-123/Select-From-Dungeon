# 游戏代码与维护器协同流程

> 文档性质：本目录仅用于流程说明。文中的请求、响应、状态编号和处理结果均为模拟内容，
> 不是运行日志，也不会调用游戏、Dungeon Maintainer、Benchmark 或外部服务。

## 一句话总览

这套项目有两条可以连起来理解的主线：玩家行为由浏览器游戏中的单一状态门面完成结算；
当代码需要排查或调整时，Dungeon Maintainer 在隔离边界内为 Coding Agent 提供有界证据，
最后由人审查 Diff 并决定是否应用。

```text
玩家操作 -> 游戏规则 -> 状态快照 -> 画面与存档
                                  |
问题描述 -> 维护器定位 -> 隔离修改 -> 检查与 Diff -> 人工决定
```

## 参与角色

| 角色 | 主要职责 | 不负责 |
| --- | --- | --- |
| 玩家 | 在真实界面移动、交互和提交 SQL | 直接修改游戏状态 |
| 浏览器游戏 | 执行 SQLite、游戏规则、渲染和本地存档 | 把隐藏答案或完整状态交给外部工具 |
| Dungeon Maintainer | 识别项目、准备隔离环境、提供受限操作与证据 | 自动发布代码或绕过授权 |
| Coding Agent | 根据规则、架构和证据定位并形成最小修改 | 自行扩大范围或接触受保护数据 |
| 评审者 | 检查 Diff、验证证据并决定后续动作 | 被默认视为已经批准发布 |

## 说明重点

1. **规则只有一个提交者。** `GameSession` 统一提交移动、战斗、课程和奖励状态。
2. **执行和判定分开。** `SqlEngine` 负责真实 SQLite 执行，学习领域负责判定结果是否满足题目。
3. **画面只消费快照。** DOM 和 Phaser 不建立第二套游戏规则。
4. **维护工作先隔离。** 维护器识别仓库后，在有界环境中定位、复现和修改。
5. **应用与发布需要另行授权。** 本地检查完成不等于代码可以进入正式分支。
