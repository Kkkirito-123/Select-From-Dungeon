## 1. 本次目标

为 `SQL 魔王城 / SELECT * FROM DUNGEON` 建立一套可以由玩法证明、由玩家调查，而不是依靠长篇
过场讲述的原创世界观。

叙事需要回答：

1. 玩家为什么用 SQL 战斗；
2. 怪物为什么以数据库记录存在；
3. 玩家为什么死亡后回到篝火；
4. 八层课程为什么通向同一个最终事故；
5. 魔王为什么阻止玩家接近王座；
6. 最终选择为什么必须由玩家已经掌握的数据库能力完成。

## 2. 用户与体验目标

| 用户 | 叙事需要提供的价值 |
|---|---|
| SQL 初学者 | 当前任务和字段保持直接，不因剧情增加理解门槛 |
| 面试复习者 | 将查询、事务、索引、MVCC 和事故处理放进一个可记忆的因果链 |
| 博客试玩者 | 在较短试玩中获得一个明确悬念，而不是先读完整设定 |
| 探索型玩家 | 可以通过环境、查询结果、遗物和人物证词主动重建历史 |
| 开发与内容维护者 | 知道什么是作者真相、玩家何时得知，以及哪些技术比喻不能误教 |

目标体验：

> 当前行动始终清楚；本层事件可以还原；世界真相允许留白。

## 3. 叙事 MVP

首个叙事版本只需要证明第一层完整闭环：

- 一个不超过三行的开场悬念；
- 玩家在身份记录中查不到自己的异常；
- 一个与篝火有关的可验证异常；
- 一名承担复盘功能的叙事角色或记录；
- 两条必然获得、使用不同渠道表达的关键证据；
- 第一层 Boss 对玩家身份异常作出反应；
- 层末只提出下一层问题，不解释完整世界真相；
- 玩家可选查看的本地《失名录》低保真入口。

第一层切片确认有效前，不批量制作其余七层台词、剧情遗物和结局演出。

## 4. 不做什么

- 不把游戏改成长篇视觉小说。
- 不要求玩家阅读外部 Wiki 才能理解当前目标或主线因果。
- 不把关键真相放进低概率掉落、随机遭遇或可永久错过的死路。
- 不让剧情改变 SQL 的真实结果或掩盖判题原因。
- 不在叙事第一版增加 Agent、模型 API、账号、后端或联网记录。
- 不因为使用数据库比喻，就声称 SQLite 能直接证明 MySQL/InnoDB 的内部行为。
- 不复制《黑暗之魂》的火之时代、传火、人物、地名、台词或具体情节。
- 不在剧情圣经中维护逐件装备数值、掉率和完整课程答案。

## 6. 当前不可破坏的产品边界

以下内容属于 `CURRENT`，具体规则以现有产品、代码和测试为准：

- SQL 是战斗动作，查询结果与课程锁共同决定攻击是否成立。
- 游戏拥有八层学习路线，最终层进行多阶段事故诊断。
- 玩家死亡后回到最近休息的篝火或本层入口，不重置整局学习进度。
- 答案复盘只使用浏览器本地记录，不调用 AI。
- Seed 必须稳定；刷新不能重抽地图、遭遇或奖励。
- 必修课程、关键武器、钥匙和主线推进不能依赖随机掉落。
- 怪物显示名称保持简短、直接、容易输入。
- 查询证据、字段、错误原因和提示必须清楚，氛围不能压过教学。

### 6.1 `v1.1.0` 运行时基线

叙事设计必须以玩家实际能运行到的内容为基线，不能把尚未接入的内容池写成已实现。

| 范围 | 当前运行事实 |
|---|---|
| 第一层 | `SELECT / FROM → WHERE / AND → IS NULL → COUNT / GROUP BY → HAVING` |
| 第二层 | `ORDER BY / LIMIT → DISTINCT → INNER JOIN → LEFT JOIN / IS NULL → JOIN 综合` |
| 第三至八层 | JOIN 深化 → 子查询与 CTE → 窗口函数 → 写操作与事务 → 索引与执行计划 → 综合事故诊断 |
| 地图 | 每层一张 `64×48` Seed 连续迷宫，叠加三个生态区域、三个篝火和两个区域门 |
| 随机掉落 | 普通怪 `2%`、小型精英 `5%`、区域 Boss `10%`、楼层 Boss `0%`；命中后只会立即使用当前生态恢复品 |
| 固定奖励 | 课程武器、课程道具与楼层钥匙按课程节点确定获得 |
| 存档 | 保存地图、篝火、怪物血量、背包、课程和答案记录；尚无剧情旗标、NPC 状态或多结局字段 |

随机武器、防具、《失名录》、剧情旗标和多结局均不是当前运行事实。

### 6.2 已发现的蓝图漂移

`CONFIRMED — 目标方向，尚未实现`

长期课程蓝图希望按“第一层单表查询、第二层聚合、第三层连接”组织；当前可执行内容则在第一层
已经进入聚合，第二层已经进入连接。楼层主题蓝图与当前生态名称也存在类似差异。

共同讨论已经选择长期迁移方向：

1. 课程目标调整为第一层单表、第二层聚合、第三层连接；
2. 保留余烬、湖沼、墓城、元素、黑铁、龙巢、水晶和王座八层视觉主题；
3. 主线地图改为紧凑手工区域，Seed 只改变非关键细节；
4. 课程、地图与旧存档迁移另立重大版本，不在叙事文档中暗中实现。

当前 `v1.1.0` 运行时事实保持不变，直到对应实现计划获得批准并完成验证。

## 7. 高概念

### 7.1 暂定标题

`PROPOSED`

> 《SELECT * FROM DUNGEON：最后一次回滚》

标题是否进入玩家界面仍为 `OPEN`；项目主品牌继续使用 `SQL 魔王城 / SELECT * FROM DUNGEON`。

### 7.2 一句话世界观

`PROPOSED`

> 这座城没有死者，只有仍能被查询到的人。

### 7.3 核心冲突

`PROPOSED`

古代王国为了消灭死亡，把居民身份、关系和生命状态写入一套王家档案。最后一次全城更新发生
严重错误，却既没有提交，也没有回滚。数百年来，王国一直运行在同一场未完成的事务里。

玩家最初以为目标是登上王座、击败魔王；真正目标是判断：

> 谁拥有决定世界最终版本的权力，以及是否存在比直接提交或完全回滚更安全的方案。

### 7.4 核心主题

`PROPOSED`

- 一个人是否等于关于他的那条记录；
- 查不到是否等于不存在；
- 正确结果是否必然导向正义决定；
- 保存现在与恢复过去分别会牺牲谁；
- 可撤销性不是软弱，而是一种责任；
- 性能、秩序和效率不能替代完整性、公平与证据。

## 8. 世界规则

本节是作者层面的叙事规则，不等同于真实数据库实现说明。

| 世界表现 | 数据库概念 | 机制状态 | 叙事状态 | 叙事作用 | 技术教学边界 |
|---|---|---|---|---|---|
| 王家档案 | 持久数据与身份记录 | 尚无独立运行系统 | `PROPOSED` | 王国用记录确认谁存在 | 首版不因此新增生产 Schema |
| 怪物异常 | 重复、缺失、错误关系、历史版本 | `CURRENT`：课程使用可查询数据 | `PROPOSED` | 让查询结果产生可见后果 | 不把数据错误冒充数据库自动行为 |
| 篝火休息 | `SAVEPOINT` 的叙事隐喻 | `CURRENT` | `PROPOSED` | 建立可返回的安全位置 | 第六层前只作世界比喻 |
| 死亡回归 | 回到最近稳定状态 | `CURRENT` | `PROPOSED` | 让失败属于世界规则 | 实际存档规则仍由当前系统拥有 |
| 玩家复盘 | 审计日志 | `CURRENT`：浏览器本地答案记录 | `PROPOSED` | 保存查询、结果与错误证据 | 继续只存浏览器本地 |
| 魔王守护王座 | 事务守护与写权限 | `CURRENT`：已有最终 Boss；无该身份叙事 | `CONFIRMED` | 阻止错误结果永久化 | 不把 Boss 战等同真实权限系统 |
| 第六层沙箱 | 隔离事务副本 | `CURRENT` | `PROPOSED` | 练习写入、撤销与提交 | 不污染永久课程数据 |
| 第七层路径 | 索引与执行计划 | `CURRENT` | `PROPOSED` | 揭示系统优先访问什么 | 索引不能被描述成改变逻辑结果 |
| 第八层历史版本 | MVCC / Undo 的教学模拟 | `CURRENT`：确定性事故 fixture | `PROPOSED` | 还原多个相互冲突的过去 | 明确标注非 SQLite/InnoDB 实证 |
| 真结局迁移 | 备份、验证、迁移、切换、回滚方案 | 尚未实现 | `CONFIRMED` | 避免在损坏的当前版本上二选一 | 不是一条神奇 SQL 命令 |

### 8.1 `???`、`NULL` 与实际值

`PROPOSED`

《失名录》必须区分：

```text
???       尚未查询，玩家没有证据
NULL      已经查询，并确认该值不存在
实际值    已经查询并获得结果
```

这三个状态不能在文案、颜色或逻辑中混为一谈。

## 9. 三个核心谜题

### 9.1 玩家为什么没有主键

`CONFIRMED — 目标叙事，尚未实现`

玩家不是王国主表中的一个居民，而是撤销历史里大量被删除、覆盖和回滚记录形成的人形残留。
因此系统无法用一条当前记录稳定定位玩家。

作者层面的表达：

```text
查询玩家：0 rows
删除玩家：0 rows affected
玩家实体：仍然存在
```

叙事后果：

- 不同怪物可能把玩家认作不同的人；
- 玩家死亡后仍能从稳定状态恢复；
- 玩家不以特殊 `id = 0` 表示，避免破坏可见短 ID 规则；
- 玩家沉默不是失忆套路，而是无法确认众多历史声音中哪一个属于“自己”。

已否决方案：

1. “档案官故意移除主键的孩子”会把集合身份缩回单一血缘谜题；
2. “王座生成的恢复程序”会让人物过度等同工具，削弱旧记录共同形成自我的主题；
3. “普通居民的记录被恶意删除”无法解释玩家携带多段互相冲突的历史。

除非通过新的决策记录撤销 `N-01`，以上方案不再参与实现选择。

### 9.2 最后的档案官为什么拒绝提交

`PROPOSED`

国王要求把全体居民更新为永远存活。执行途中出现身份覆盖、重复复活、关系错接和历史版本清除。

档案官确认：

- 直接 `COMMIT` 会把损坏状态永久化，并让许多旧版本无法恢复；
- 完全 `ROLLBACK` 会抹去数百年来依靠错误记录产生的新生命；
- 继续保持事务开放会让所有人持续承受循环与不确定性。

她拒绝提交，却也没有能力完成安全迁移。这个选择保存了反悔的可能，同时制造了数百年的苦难。
她不是纯粹英雄，也不是单纯反派。

### 9.3 魔王在保护谁

`CONFIRMED — 目标叙事，尚未实现`

魔王是最后的档案官与王座守护系统长期融合后的形态。

她保护的不是国王，也不是当前秩序，而是所有已经不在当前记录中、却仍可从历史版本恢复的人。
其中也包括玩家。

最终冲突不是“玩家是否足够强”，而是：

> 玩家是否已经证明自己能够在不销毁证据的前提下取得写权限。

已否决方案：

1. “独立守护程序、档案官已死”会削弱她为长期停滞承担责任的情感冲突；
2. “魔王就是国王”会把最终冲突重新简化为推翻暴君；
3. “档案官仍是未变化的普通人”无法解释她与王座、权限和时间的长期融合。

除非通过新的决策记录撤销 `N-02`，魔王固定为最后档案官与王座守护系统融合后的同一人物。

## 11. 核心人物

首版不单独建立人物文档；人物超过当前规模后再拆分。

### 11.1 无键者

`PROPOSED`

- 身份：玩家；当前表中没有稳定对应记录。
- 表面目标：登上王座，结束魔王造成的循环。
- 内在问题：如果自己由许多旧版本组成，是否仍然可以成为一个人。
- 玩法关系：玩家每掌握一种查询能力，就能确认更多关于世界和自己的事实。
- 表达限制：不使用复杂称号堆砌神秘感；“无键者”只在剧情语境中使用，不替代玩家自定义名。

### 11.2 抄写员

`PROPOSED`

- 身份：篝火附近负责复盘的记录人格。
- 功能：把本地答案复盘转化为世界内行为，但不改变当前复盘证据。
- 初始认知：自称仍在执行档案工作。
- 隐藏真相候选：本人早已死亡，玩家交谈的是保存下来的响应记录。
- 文案边界：每次只反馈一个事实和一个疑点，不代替老师讲完整答案。

### 11.3 守墓人

`PROPOSED`

- 身份：第三层的中立见证者。
- 功能：提出“查不到是否等于不存在”的伦理问题。
- 立场：更相信墓碑、遗物和人与人的记忆，而不是王家记录。
- 局限：墓碑和记忆也可能错误，因此他的证词不是绝对真相。

### 11.4 最后的档案官 / 魔王

`CONFIRMED — 核心身份已确认，具体台词与外观尚未确认`

- 身份：拒绝执行最终提交、并与王座守护系统长期融合后的最后档案官。
- 表面目标：阻止任何人进入王座。
- 真实目标：保留历史版本和安全恢复的可能。
- 主要错误：把“还不能安全决定”延长成数百年的停滞。
- 最终考验：要求玩家证明自己会查询、验证、计划、回滚和处理事故，而不只是造成更高伤害。

### 11.5 国王

`PROPOSED`

- 首版主要通过命令、雕像、官方记录和后果存在，不需要成为频繁对话 NPC。
- 动机不是简单追求力量，而是无法接受大规模死亡与失去控制。
- 他的方案解决了“死亡”，却把人降格为可以被覆盖和排序的记录。
- 国王是否仍以某种版本存在于第八层，保持 `OPEN`。

## 12. 结局候选

结局结构为 `PROPOSED`；首个叙事 MVP 不实现完整多结局。

### 12.1 `COMMIT`：保存现在

- 把当前损坏但仍在运行的世界永久化；
- 现存生命获得稳定身份；
- 旧历史版本被清理；
- 玩家作为历史残留随之消失。

主题：秩序与不可逆。

### 12.2 `ROLLBACK`：恢复过去

- 回到永生计划之前的稳定状态；
- 普通死亡重新成立；
- 过去的人可能恢复；
- 数百年来由错误记录产生的新生命消失。

主题：修复与代价。

### 12.3 `LEAVE OPEN`：继续等待

- 玩家拒绝提交也拒绝回滚；
- 玩家代替魔王守护事务；
- 世界继续循环。

主题：保留可能与逃避决定。

### 12.4 `MIGRATE`：最后一次迁移

`CONFIRMED — 推荐真结局，尚未实现`

玩家拒绝在损坏的当前世界上直接二选一：

1. 保存只读快照；
2. 审计冲突与缺失记录；
3. 保留历史版本；
4. 在隔离环境构建新结构；
5. 验证数量、关系、约束和访问路径；
6. 切换到新版本；
7. 保留明确回滚方案。

主题：成熟的工程判断不是找到一条万能命令，而是建立安全、可验证、可恢复的过程。

## 13. SQL 与叙事的对应

具体课程归属仍由课程文档拥有；本表只定义叙事用途。

| SQL / 数据库能力 | 叙事动作 |
|---|---|
| `SELECT` | 读取世界允许玩家看到的事实 |
| `WHERE` | 从众多记录中准确锁定当前目标 |
| `NULL` 判断 | 区分未知、未查询和确认不存在 |
| 聚合 | 发现个体被统计数字掩盖后的异常 |
| `JOIN` | 恢复人物、尸骨、房间与遗物之间的关系 |
| 子查询 / CTE | 追查依赖另一个结果的幕后来源 |
| 递归 CTE | 沿主人或命令链追踪到王家档案 |
| 窗口函数 | 重建排名、前后版本和历史顺序 |
| 写操作 / 事务 | 理解改变世界、撤销错误与提交的边界 |
| 索引 / 执行计划 | 检查系统如何寻找事实，而不是改变事实 |
| MVCC / 锁 / 隔离 | 还原多个同时成立却彼此冲突的版本 |
| 建模 / 安全 | 判断谁可以写、如何验证以及怎样保留恢复路径 |

## 14. 叙事交付规则

### 14.1 清晰度分层

| 层级 | 清晰度目标 |
|---|---:|
| 当前去哪里、查询什么、为什么战斗 | `100%` 清楚 |
| 本层发生过什么、Boss 为什么存在 | 大部分可以还原 |
| 王国完整历史与人物动机 | 通过跨层证据逐步确认 |
| 哲学解释和个别人物命运 | 允许合理留白 |

### 14.2 证据规则

- 每个主线真相至少由两种不同渠道支持。
- 必看证据不得依赖随机遭遇、随机掉落、隐藏门或外部资料。
- 可选证据可以深化人物，但不能推翻玩家已经依赖的明确教学事实。
- 环境、SQL 结果、NPC 证词和遗物可以互相矛盾；矛盾必须能够被更高质量证据解释。
- 不能用“也许一切都是梦”回避已经建立的因果。

证据渠道：

1. SQL 查询与结果；
2. 地图、摆放和怪物状态；
3. 人物短对话；
4. 遗物与《失名录》；
5. Boss 阶段和系统反馈。

### 14.3 文本预算

| 场景 | 首版预算 |
|---|---:|
| 新游戏开场 | 最多 3 行 |
| 楼层标题与目标 | 2–3 行 |
| 普通怪异常反馈 | 1 行 |
| Boss 战前 | 最多 4 行 |
| Boss 战后 | 最多 5 行 |
| 物品说明 | 世界观 1 行 + 准确效果 1 行 |
| 篝火反馈 | 一个事实 + 一个疑点 |
| 长文本 | 只进入可选《失名录》 |

### 14.4 语气

`PROPOSED`

- 主体是克制、悲剧性的数据库奇幻；
- 重要台词直白，不用大量专有名词制造深度；
- 怪物名字保持简单，SQL 意义放进字段、目标和结果；
- 允许少量温暖和冷幽默，避免全程压抑；
- 技术词在教学界面准确，在人物台词中只在角色确实理解时使用。

## 15. Seed、地图与掉落的叙事边界

本节只记录叙事约束，不定义实现参数。

### 15.1 Seed

`CONFIRMED — 目标方向，尚未实现`

- 主线真相、关键角色、Boss、课程和必看证据固定；
- 必修锚点顺序、主线连接、地区宏观轮廓和捷径关系固定；
- Seed 只选择已审核的局部房间、非关键支路、普通遭遇、非关键奖励和装饰变体；
- 相同 Seed 必须得到相同的可观察结果；
- 世界内可把 Seed 表达成一次“恢复路径”或“执行路径”，但不强迫玩家理解该比喻。

### 15.2 地图

`CONFIRMED — 目标方向，尚未实现`

- 先定义每层必须发生的事件，再生成连接事件的空间；
- 地图承担叙事证据，不只是更换颜色；
- 主线采用手工宏观拓扑，Seed 只改变装饰、普通怪和非关键资源；
- 第一层先通过管理员模式验证区域 Blockout、三个篝火和两条捷径，不立即重做八层；
- 具体距离、安全区、门户和地图尺寸继续由地图契约拥有。

### 15.3 掉落

`CURRENT`

- 当前低概率随机恢复品规则保持事实边界，除非另行批准重做；
- 关键装备、课程奖励、钥匙和剧情证据不随机；

`PROPOSED`

- 剧情遗物不占普通装备背包；
- 随机装备、越阶武器和多件保底掉落属于未来候选，不能从历史设计稿恢复为当前规则；
- 第一层切片只设计支持本层闭环的最少物品。

## 16. 玩家可见开场候选

`PROPOSED`

所有名字都被保存在王城深处。

## 18. 验收标准

剧情圣经确认时应满足：

- 能用一句话解释世界悬念；
- 能明确回答玩家、档案官和魔王的关系；
- 死亡、篝火、复盘和最终事故属于同一套因果；
- 每个数据库比喻都有技术教学边界；
- 主线目标清楚，不要求玩家先读本文；
- 没有关键真相依赖随机掉落；
- 不复制现有商业游戏的专有设定或文本；
- 已确认事实、推荐方案和开放问题可以明确区分；
- 后续揭示矩阵能够引用本文而不重新编写完整背景。

## 19. 风险与取舍

| 风险 | 处理方式 |
|---|---|
| 故事比 SQL 更抢注意力 | 保持短文案和当前任务完全清楚 |
| 数据库比喻造成误教 | 为 SQLite、MySQL/InnoDB 和虚构规则标注边界 |
| 真相过度晦涩 | 必看事实使用至少两种证据，并由《失名录》自动整理 |
| 剧情线索被随机地图隐藏 | 固定关键锚点，Seed 只改变非关键路径 |
| 多结局扩大范围 | 第一层切片不实现结局，最终只先落地一个 |
| 文档与当前运行时混淆 | 所有新文档标记“草案/未实现”，README 只写真实功能 |
| 课程重排牵动旧存档 | 单独立项，不在叙事文档 PR 中改代码或迁移 |
| 旧掉落方案被误恢复 | 继续以 `v1.1.0` 覆盖规则为当前事实 |
