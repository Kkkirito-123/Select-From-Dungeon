## 1. 叙事产品承诺

### 1.1 一句话世界观

> 这座城没有真正消失的人，只有仍能被查询、恢复或误写的人。

### 1.2 玩家承诺

玩家不是通过收集百科文本“听说”世界真相，而是通过以下动作逐步证明它：

```text
发现异常
→ 查询真实数据
→ 让世界产生可见变化
→ 比较人物说法与查询结果
→ 保存不可随机错过的证据
→ 在下一层修正上一层过于简单的结论
```

每层结束时必须同时交付：

- 一个已经由玩法证明的答案；
- 一个比本层答案更困难的新问题；
- 一次人物关系变化；
- 一项永久可追溯的图鉴或《失名录》记录。

### 1.3 叙事不做什么

- 不把主线做成长篇视觉小说。
- 不用晦涩称号代替清晰任务。
- 不复制现有商业游戏的世界、人物、台词或专有情节。
- 不把低概率掉落、随机遭遇或隐藏支路作为主线真相的唯一来源。
- 不因剧情需要改变 SQLite 的真实执行结果。
- 不把虚构世界规则描述成 SQLite、MySQL 或 InnoDB 的真实内部行为。
- 不让抄写员替玩家写 SQL、直接给答案或无条件夸奖。
- 不在第一、第二层解释玩家完整身份、魔王真相或最终结局。
- 不实现 `COMMIT / ROLLBACK / LEAVE OPEN` 多结局；当前唯一目标结局是 `MIGRATE`。

## 2. 作者真相

### 2.1 王国事故

`CANON`

古代王国试图用王家档案消灭死亡。居民的身份、居所、关系、装备、生命状态与恢复轨迹逐步被写进
同一套记录体系。国王随后命令执行一次全城永生更新。

更新过程中发生：

- 多个身份被覆盖为一条记录；
- 同一人被重复恢复；
- 人、房间、遗物与亲属关系错接；
- 当前记录与历史版本互相冲突；
- 清理历史会让仍依赖旧版本存在的人彻底消失。

最后的档案官拒绝提交，也没有完全回滚。王国从此停留在一场未完成的事务中。

### 2.2 玩家身份

`CANON`

玩家不是当前居民表里缺少姓名的一行，也不是 `id = 0` 的特殊居民。玩家是许多删除、覆盖、失败
和撤销留下的历史残留逐渐形成的人形集合。

因此以下事实可以同时成立：

```text
查询当前居民：0 rows
按当前主键删除玩家：0 rows affected
恢复轨迹：valid
玩家实体：仍然存在
```

玩家的成长不是“找回唯一旧名字”，而是理解多个旧版本如何共同形成现在的自己，并最终选择一种
不会再次抹掉证据的迁移方式。

### 2.3 魔王与最后的档案官

`CANON`

魔王就是最后的档案官与王座守护系统长期融合后的同一人物。

她保护的不是国王，而是所有已经不在当前记录中、却仍可从历史恢复的人，其中也包括玩家。她的
错误不是保存历史，而是把“尚不能安全决定”延长成数百年的停滞。

### 2.4 唯一结局

`CANON`

第八层唯一正式结局为 `MIGRATE`：

1. 保存只读快照；
2. 审计冲突与缺失；
3. 保留历史版本；
4. 在隔离环境构建新结构；
5. 验证数量、关系、约束与访问路径；
6. 切换到新版本；
7. 保留明确回滚方案。

这不是一条万能 SQL，而是一套可验证、可恢复、愿意承担后果的工程过程。

## 3. 世界规则

### 3.1 记录与存在

- 当前记录是证据，不是一个人的全部。
- 查不到不自动等于不存在。
- 查询正确不自动等于决定正义。
- 多条相同值可能是重复数据，也可能来自不同生命；必须继续调查来源和关系。
- 效率不能替代完整性，完整性也不能替代明确的决定责任。

### 3.2 `???`、`NULL` 与实际值

三者必须在逻辑、文案和视觉上严格区分：

| 显示 | 含义 | 玩家能否下结论 |
|---|---|---|
| `???` | 尚未查询或证据不足 | 不能 |
| `NULL` | 已查询并确认该字段没有值 | 可以确认“缺失” |
| 实际值 | 查询获得具体记录 | 可以引用该值 |

任何角色不得把 `???` 说成 `NULL`，也不得把 `NULL` 说成“这条记录不存在”。

### 3.3 篝火与死亡

篝火是稳定恢复点和 `SAVEPOINT` 的世界隐喻，不是对真实数据库实现的说明。

死亡规则：

```text
本场生命归零
→ 回最近休息篝火；未休息则回出生安全区
→ 本场未结算阶段复原
→ 已经永久结算的名字、图鉴、主线证据与捷径不撤销
→ 玩家可查看本场错误和本层复盘
```

死亡不是角色在剧情中反复真正死亡，也不重置整层历史。

### 3.4 Seed

- 主线人物、Boss、证据、剧情结论和关键拓扑固定。
- Seed 只能改变已审核的装饰、普通遭遇、非关键支路和恢复品。
- 同 Seed 必须得到相同可观察结果。
- 随机结果不能制造互相冲突的作者真相。

## 4. 核心主题

| 主题 | 玩家通过什么理解 | 反面表达 |
|---|---|---|
| 自我由历史形成 | 名字、关系、版本与错误逐层汇合 | “找到真名就全部解决” |
| 查不到不等于不存在 | 第一层 0 行与有效恢复权限 | 神秘力量无条件例外 |
| 相同不等于可覆盖 | 第二层七个来源与共同轨迹 | 用 `DISTINCT` 直接删除生命 |
| 关系决定意义 | 第三层 JOIN 深化 | 只看孤立记录 |
| 改变必须可撤销 | 第六层事务沙箱 | 把高伤害等同正确修改 |
| 路径包含权力 | 第七层索引与计划 | 把性能唯一化为正义 |
| 责任来自可验证过程 | 第八层迁移 | 一键提交或一键回滚 |

## 5. 叙事交付原则

### 5.1 行动先于解释

每个主线节拍至少包含以下三项中的两项，层结论必须包含全部三项：

1. SQL 结果；
2. 地图或角色可见变化；
3. 图鉴、日志或《失名录》的永久证据。

只弹出文本卡不算完成一个剧情事件。

### 5.2 双渠道证据

每个主线结论至少由两个不同渠道证明：

- 查询与结果；
- 环境状态；
- 角色行动或短对话；
- Boss 机制；
- 图鉴、遗物或《失名录》。

第一层使用“查询 0 行 + 篝火有效恢复”，第二层使用“七个不同来源 + 七个独立倒影”。

八层各有一个可错过的实体隐藏区域，用同层已学语法打开，并提供额外实物证据与确定性专属换装。
隐藏证据只能强化主线结论，不能成为结论成立、课程通关、Boss 开门或换层的唯一条件。

### 5.3 当前目标百分之百清楚

允许世界真相留白，但以下信息不得留白：

- 去哪里；
- 调查哪个对象；
- 使用哪张表；
- 字段属于哪张表；
- 是否需要别名；
- 成功后世界发生什么。

### 5.4 文本预算

| 场景 | 首次文本预算 | 重复交互预算 |
|---|---:|---:|
| 新游戏开场 | 3 行 | 不重复 |
| 楼层入场 | 2–3 行 | 1 行目标 |
| 普通调查 | 1–2 行 | 1 行事实 |
| 怪物胜利 | 名字 + 1 行生态 | 图鉴入口 |
| 篝火 | 一个事实 + 一个疑点 | 菜单状态 |
| Boss 战前 | 4 行以内 | 1 行阶段目标 |
| Boss 战后 | 5 行以内 | 日志入口 |
| 长文本 | 只进入可选图鉴或《失名录》 | 可重读 |

### 5.5 语气

- 克制、温柔、悲剧性，但当前行动直接。
- 抄写员的温暖来自记得、诚实和等待，不来自哄玩家。
- Boss 说话像执行错误规则，不使用空泛威胁。
- 怪物名字直白、容易读写；深度来自环境和关系。
- 允许一两处生活感和轻微冷幽默，避免全程压抑。

### 5.6 技术边界

虚构比喻首次出现时不必弹教学警告，但复盘与图鉴必须准确：

- `NULL` 不是空字符串，也不是“尚未查询”；
- `DISTINCT` 只作用于查询结果值，不判断生命价值；
- `JOIN` 条件错误可以产生错误关系，但不会让数据库自动长出树根；
- 索引改变访问路径，不改变正确查询的逻辑结果；
- 篝火、Undo 人形和王国事务均为叙事隐喻。

## 6. 身份揭示协议

### 6.1 怪物身份状态机

| 状态 | 世界标签 | 地图常亮 | SQL 结果 | 图鉴 |
|---|---|---|---|---|
| `UNKNOWN` | `ID #xxx` | ID、HP、意图 | 只显示当前题所需数据 | 未发现轮廓 |
| `PENDING` | `ID #xxx` | 仍只显示 ID | 最后一击可返回姓名字段，但不提前改世界标签 | 等待结算 |
| `DISCOVERED` | `真名 · ID #xxx` | 真名与 ID | 可正常引用 | 永久解锁 |

硬规则：

1. 胜利结算提交前，地图标签、遭遇卡、任务标题、NPC 台词、日志标题和无障碍名称都只能使用 ID。
2. 任何需要查询 `name` 的题，应把姓名查询放在最后一击阶段；旧题若提前返回姓名，必须调整阶段顺序或返回字段。
3. 首次恢复名字的顺序固定为：最终查询结果→目标行高亮→敌人归零→名字恢复演出→写入永久图鉴。
4. 玩家逃跑、关闭终端或战斗失败时，不提交 `DISCOVERED`。
5. 图鉴已永久解锁的怪物在新 Run 可以显示真名，但不得泄露尚未学习的完整答案。
6. 同名生态个体可共享通俗名字，但 ID、栖息地和形态必须区分。

### 6.2 玩家旧名字

第二层的七个旧名字属于身份调查证据，不是当前玩家名，也不是怪物真名。展示时：

- 每个名字必须绑定来源地点或记录渠道；
- 不允许 UI 将其中一项标成“真名”；
- 不允许自动选择出现频率最高者；
- 离开第二层时仍保持七页并列。

### 6.3 图鉴与《失名录》分工

| 系统 | 保存内容 | 不保存什么 |
|---|---|---|
| 怪物图鉴 | 已发现真名、ID、栖息地、生态、课程、世界线索 | 未击败真名、主线完整答案 |
| 《失名录》 | 主线身份证据、`???/NULL/值` 状态、证据来源 | 怪物掉落百科、完整 SQL 答案 |
| 答案复盘 | 本层实际查询、结果、错误与提示使用情况 | AI 推测、虚构对话 |
| 任务日志 | 当前目标、已完成事件与可回访目标 | 作者视角真相 |

## 7. 人物弧

### 7.1 无键者 / 玩家

| 阶段 | 楼层 | 表面认知 | 角色变化 |
|---|---:|---|---|
| 异常 | 1 | “我只是丢了名字。” | 接受当前表中没有自己，但拒绝把 0 行当作不存在 |
| 复数 | 2 | “七个名字里必有一个是我。” | 学会保留不同来源，不急于选择唯一答案 |
| 关系 | 3–4 | “这些记录彼此无关。” | 发现关系与共同命令 |
| 责任 | 5–6 | “知道事实就能直接修复。” | 理解顺序、权限、回滚与副作用 |
| 判断 | 7–8 | “找到最快路径就够了。” | 以证据完成可验证迁移，主动定义现在的自己 |

玩家可以保持少言，但不能没有选择痕迹。其性格由调查、保留证据、是否完成支线以及最终工程步骤
体现，而不是由大量对白选项体现。

### 7.2 抄写员

`IMPLEMENTED_F1_F8`：每层只有一个人物实体，随剧情移动；篝火菜单不是她的复制体。

| 阶段 | 楼层 | 初始立场 | 可见行动 |
|---|---:|---|---|
| 建立信任 | 1–2 | 相信登记制度可以解决异常 | 为 0 行对象留页；拒绝合并七份记录 |
| 产生怀疑 | 3–4 | 相信保存全部记录就足够 | 请求外部见证；隐瞒一段档案官签名 |
| 正面冲突 | 5–6 | 害怕玩家取得写权限 | 反对错误公开顺序；主张完全回滚，后接受沙箱验证 |
| 共同决定 | 7–8 | 承认保存方式也包含取舍 | 公开签名与证据；交出决定权并保留审计责任 |

作者真相中她是否为真人、保存人格或单一载体仍为 `OPEN`。八层运行时只证明：

- 她有唯一连续位置；
- 她需要实际移动或乘坐交通；
- 她会承认过去判断有错；
- 她不会瞬移成多个功能副本。

### 7.3 第一层登记官

内部制作名：登记官；玩家击败前只见 `ID #005`。

- 相信有效恢复必须对应当前居民行。
- 将 0 行误判为不存在，并试图注销玩家权限。
- 结局不是被杀死，而是停止执行错误规则。
- 它证明制度可以诚实执行错误前提。

### 7.4 第二层灯塔守卫

内部制作名：灯塔守卫；玩家击败前只见 `ID #014`。

- 为保证航路稳定，只保留最强、最多的信号。
- 将同一规则错误地用于身份档案。
- 结局不是摧毁灯塔，而是让它同时照亮七个来源。

### 7.5 后续人物

- 守墓人：独立 NPC 方案延后；第三层 V1 由墓志、遗物和抄写员共同承担外部见证，不新增重复功能人物。
- 最后的档案官 / 魔王：第八层承担最终责任冲突。
- 国王：主要通过命令、雕像和后果存在；是否仍以某版本存活为 `OPEN`。

## 8. 八层宏观揭示矩阵

八层宏观顺序以[八层主线精排](./EIGHT_FLOOR_STORY_ORDER.md)为准；每层的地图、短对白、隐藏区和
SQL 密文门以对应逐事件脚本与运行时体验定义为准。

| 层 | 地点与核心动词 | 本层问题 | 必须由玩法证明 | 抄写员变化 | 层末结论 |
|---:|---|---|---|---|---|
| 1 | 地下余烬档案；调查、排水、回返 | 当前表没有玩家，火为何仍能恢复？ | `0 rows`、有效权限、水位、回执分组 | 为无当前记录者建立第一页 | 玩家属于仍可恢复的历史 |
| 2 | 潮汐群岛；航行、选岛、改潮 | 七个名字是重复还是不同来源？ | 排序浮标、去重频道、连接地点、七个倒影 | 拒绝把相似记录合并 | 共同轨迹不等于同一条记录 |
| 3 | 白霜墓原；侦查、对照、还原 | 这些来源彼此是什么关系？ | 双状态证据、自连接、三表关系 | 首次请求外部见证 | 多个旧身份存在真实关系 |
| 4 | 元素升炉；追踪、接线、断路 | 不同异常来自哪里？ | 子查询、CTE、递归命令链 | 发现并隐瞒档案官签名 | 异常来自同一历史命令 |
| 5 | 黑铁轮值城；潜入、观察时序 | 正确事实何时公开才不伤人？ | 排名、前后岗次、累计警戒与绕战 | 反对立即公开全部记录 | 顺序和优先级也有代价 |
| 6 | 龙脊回滚工坊；预演、修改、回滚 | 保存现在和恢复过去谁更正确？ | 沙箱写入、约束、回滚、Savepoint | 主张回滚，后接受验证 | 直接二选一都会抹掉生命 |
| 7 | 残照索引王苑；比较路径、验证 | 存在的记录为何仍找不到？ | 扫描路、索引路、执行计划 | 承认保存方式也影响可见性 | 访问路径体现权力与取舍 |
| 8 | 黑金迁移高堂；诊断、迁移 | 谁能安全决定最终版本？ | 七翼证据、五阶段事故、MIGRATE | 不再代为总结，只核验证据 | 玩家是历史集合，并承担迁移责任 |

## 9. 第一层叙事锁定

详细执行以[第一层逐事件脚本](./FLOOR_01_SCRIPT.md)为准。

### 9.1 问题、答案与下一问

- 问题：当前居民表中没有玩家，为什么篝火仍能恢复玩家？
- 答案：玩家不属于当前居民表，但属于一段仍有效的恢复历史。
- 下一问：那段历史中到底有几个名字？

### 9.2 必然证据

1. 当前登记查询返回 `0 rows`，恢复权限灯同时显示 `VALID`；
2. `monster_signals` 的多个来源经 `GROUP BY / HAVING` 形成有效恢复轨迹；
3. 登记官无法用当前主键注销玩家；
4. 《失名录》第一页由抄写员主动保留。

可选强化证据：封存旧库中的未登记旧页仍盖有有效恢复印。它证明“当前缺席不等于历史无效”，
但玩家即使没有发现旧库，也必须能从四项必然证据完成第一层。

### 9.3 人物变化

抄写员从“没有记录就不能登记”转向“没有当前记录也必须保留证据”。她第一次离开桌子，在捷径
回访时走向登记厅，并在层末亲手装订第一页。

## 10. 第二层叙事锁定

详细执行以[第二层逐事件脚本](./FLOOR_02_SCRIPT.md)为准。

### 10.1 问题、答案与下一问

- 问题：多个旧名字共享一条恢复轨迹，它们是重复，还是不同的人？
- 答案：这些记录来自不同地点和渠道，不能因轨迹相同而覆盖。
- 下一问：它们之间是什么关系，又曾经属于谁？

### 10.2 必然证据

1. `ORDER BY` 只确定信号优先级，不能决定身份真实性；
2. `DISTINCT` 证明存在多个值，但不证明哪个值应被删除；
3. `JOIN` 将名字分别连接到不同地点和记录来源；
4. 退潮回访时七盏浮标与七个倒影同时出现；
5. 灯塔守卫的“只留多数”规则被修正，七束光同时保留。

可选强化证据：沉船记录舱中的七只防水匣来自不同港口，却共享一条返航轨迹。它用于反驳“同轨迹
就是同一个人”，但不提前发放七个旧名字，也不替代灯塔结论。

### 10.3 人物变化

抄写员承认自己过去也曾把相似记录装订成一页。她在层末分别编号七页，不替玩家选一个真名。

## 11. 第三层叙事锁定

详细执行以[第三层逐事件脚本](./FLOOR_03_SCRIPT.md)为准。

### 11.1 问题、答案与下一问

- 问题：第二层发现的不同来源彼此是什么关系？
- 答案：名字和当前主人可以缺失，真实关系仍能通过多表连接恢复。
- 下一问：为什么不同关系最终都接入同一座仍在运行的升炉？

### 11.2 必然证据

1. `INNER JOIN` 让断裂骨桥重新连接怪物与墓室；
2. `LEFT JOIN / IS NULL` 保留没有装备记录的对象；
3. 自连接为同一张表中的死者与主人提供两个清晰身份；
4. 三表链将死者、墓室与遗物变成可见证据链；
5. `UNION` 保留互相冲突的两组证词；
6. 最终审计阻止“只能留下一个继承人”的错误规则。

无主遗物室是可选强化证据，不承担主线结论，也不发放本层专属换装。

### 11.3 人物变化

抄写员第一次承认“保存记录”本身仍可能保留错误关系。她开始把字段间的来源写在页边，而不是只
抄录最终值。

## 12. 第四层叙事锁定

详细执行以[第四层逐事件脚本](./FLOOR_04_SCRIPT.md)为准。

### 12.1 问题、答案与下一问

- 问题：火、冰、雷是三场灾难，还是同一次命令的不同结果？
- 答案：它们沿递归依赖链回到同一条尚未完成、也未回滚的历史命令。
- 下一问：谁在阻止命令结束，为什么直接公开、提交或回滚都可能伤害仍存在的人？

### 12.2 必然证据

1. 标量子查询定位共同命令源；
2. `IN` 和 `EXISTS` 区分集合成员与真实存在的明细；
3. 相关子查询让每条外层记录只读取自己的依赖；
4. CTE 为共享依赖命名；
5. 递归 CTE 追到完整命令链；
6. `ID #044` 倒下后，第一层余烬残响证明旧层火种也属于同一依赖。

回燃残响是可选探索内容，不改变第一层真实进度。专属护甲“回燃衣”是确定奖励，装备后改变玩家
像素轮廓与色板，但不成为主线通关条件。

### 12.3 人物变化

抄写员认出一段与最后档案官有关的签名，却没有立刻公开。她第一次从“证据保存者”变成需要为
披露时机负责的人，为第五层的顺序与权力主题建立冲突。

## 13. 叙事状态与存档契约

### 13.1 提交时机

| 内容 | 提交时机 | 死亡是否回滚 |
|---|---|---|
| 战斗阶段输入 | 当前回合 | 回到战前阶段 |
| 怪物真名 | 胜利结算完成 | 否，永久图鉴保留 |
| 主线证据 | 对应事件完成 | 否 |
| 水位、潮位、捷径 | 世界演出完成 | 否 |
| 隐藏区域门 | 同层前置课程完成并在实体入口交互 | 否 |
| 本场临时镜头和特效 | 不持久化 | 是 |
| 抄写员位置 | 优先由故事阶段派生 | 按阶段恢复 |
| 可选对话已读 | 不阻塞主线 | 可以重复或缩短 |

### 13.2 读档恢复

读档后不得重播已经确认过的完整演出。系统应：

- 恢复最终环境状态；
- 将角色放在该阶段合法位置；
- 用一行日志提示已完成事件；
- 保留重看图鉴与《失名录》的入口；
- 对中断中的关键演出从安全检查点重新播放，而不是落在半开门或半退潮状态。

### 13.3 可错过边界

- 本层问题、两条主证据、名字恢复、Boss 结论和下一层入口不可错过。
- 支线 Boss、额外生态、服装和补充日志可以错过，但后续必须可以回访。
- 可选内容不得推翻主线已经确认的事实。

## 14. 音频、镜头与可访问性叙事规则

- 镜头只用于建立地点、强调查询结果对应物和确认状态变化。
- 不用长时间锁镜头隐藏玩家目标；关键演出可跳过。
- Reduced Motion 下将移动、抖动和粒子替换为淡入、轮廓闪白、字幕与状态文字。
- 静音时，浮标、篝火、门锁、名字恢复和 Boss 阶段必须有同等视觉/文字反馈。
- 对话字幕不与 SQL 结果争夺同一视觉焦点。
- 角色或怪物首次出现不能只靠音乐提示。
- 名字发现的无障碍播报必须在胜利提交后发生。

## 16. 验收标准

### 16.1 世界与人物

- 团队成员能用两句话说清事故、玩家身份与最终档案官关系。
- 第一层不提前解释七个名字，第二层不提前解释它们的关系。
- 抄写员在任一时间只有一个合法人物位置。
- 八层每层恰好完成一次核心人物变化。
- 八层每层恰好有一个可错过的实体隐藏区域，入口、室内语法和证据主题彼此不同。
- 八层每层恰好有一个可选 SQL 密文门；成功永久开路，错误只反噬 1 点且不授予课程、XP 或掉落。
- 第四层中层首领必须先于回燃门出现，且回燃门只进入压缩残响，不切换第一层真实状态。

### 16.2 身份与证据

- 自动检查所有遭遇标题、地图标签、对白和无障碍名称：击败前不得出现真名。
- 所有姓名查询位于最后一击阶段，或在胜利前不改变世界身份状态。
- 每个主线结论拥有至少两种不同证据渠道。
- 必然证据不依赖 Seed、随机掉落或可错过支线。

### 16.3 失败、重复与读档

- 每个关键事件都定义首次、重复、错过、死亡和读档行为。
- 战斗失败不会解锁名字或提交半完成环境状态。
- 已完成名字、证据、捷径和 Boss 结果不会因后续死亡丢失。
- 读档不会重复发奖，也不会把角色放进非法位置。

### 16.4 教学与可访问性

- 剧情台词不替代字段、表、别名和连接条件说明。
- 静音、Reduced Motion、键盘和触屏均能理解同一剧情状态。
- 长文本只进入可选页面，不阻塞 SQL 输入。
- 图鉴不泄露尚未学习的完整答案。

## 17. 后续冻结点

在制作第五层逐句脚本前必须裁决：

1. 抄写员的作者层真实形态；
2. 国王是否仍以某个版本存在；
3. 抄写员隐瞒签名在第五层何时、以何种玩家可验证方式暴露；
4. 七个旧名字是否需要固定玩家可见文本，或只使用编号与来源；
5. 第八层最终写权限的具体仪式和无障碍替代。

这些开放项不阻塞八层运行，也不得被现有对白提前暗示成唯一答案。
