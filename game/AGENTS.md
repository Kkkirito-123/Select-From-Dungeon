# Stable Rules for Game Coding Agents

This file is the stable operating authority for `game/`. Read the repository
root `AGENTS.md` first. Read `ARCHITECTURE.md` before implementation that
depends on game ownership, flow, commands, data, compatibility, or runtime
facts. `AGENTS.zh-CN.md` is the synchronized Chinese translation.

## Authority and Reading Order

1. Read root and this `AGENTS.md`.
2. Route through the applicable repository Skill.
3. For approved L1/L2 work, read the exact root `TASK.md` contract and its
   `ARCHITECTURE_REF`.
4. Read only the owning source, tests, contracts, and documentation needed for
   the bounded change.

Source and executable tests are evidence of current behavior. The approved
Task is evidence of intended behavior. Report material drift instead of
silently choosing one source.

## Working Contract

- Reply in Chinese unless the user requests another language. Use UTF-8;
  identifiers, APIs, and tests follow the codebase language.
- Serve one explicit objective at a time and define observable success before
  editing.
- Preserve unrelated user work. Do not overwrite, roll back, delete, publish,
  reformat, or expose unrelated content without explicit authorization.
- Features, refactors, deletions, dependency or schema changes, batch edits,
  global configuration changes, and other high-impact work require an approved
  objective, scope, acceptance criteria, validation, and risk boundary.
- Prefer the smallest coherent vertical slice. Do not add speculative features,
  abstractions, compatibility paths, dependencies, or duplicate authorities.
- Distinguish implementation, environment, validation-path, and tool failures.
  Do not repeat a materially identical failed attempt more than three times.
- Claim only checks that actually ran and distinguish unit, type, build,
  browser, provider, device, and end-to-end evidence.
- Local inspection and validation do not authorize Commit, Push, PR,
  deployment, destructive actions, or other external writes.

## Game Boundaries

- Keep dependencies pointing toward parent contracts and shared rules. Domain,
  content, and infrastructure must not import application, presentation, or
  devtools implementations. Pure runtime constants are supplied one-way by
  `contracts/config`. Extend `scripts/check-architecture.mjs` for new boundaries.
- `.maintainer/architecture-map.json` is the game-owned machine routing authority
  for stable areas, responsibility partitions, cross-layer features, and the
  eight `floorScopes`; it is not a code index. A floor child must not import a
  sibling floor. Shared logic moves to a parent service partition and one registry
  composes the children. Ordinary files and internal folders do not update the
  map; stable roots, responsibilities, or routes do.
- `GameSession` and focused domain modules own game rules. DOM and Phaser code
  render snapshots and forward explicit intent; they must not become a second
  rule engine or storage owner.
- The browser game must remain playable without the optional Python Agent.
  Cross-project behavior uses the strict HTTP contract only; do not create
  shared source imports or a hidden second runtime path.
- Generated question banks and transformed assets are reproducible outputs.
  Change their authored sources and generators, never generated bytes by hand.
- Storage-shape, protocol, public-contract, generated-code ownership, command,
  module, security, or runtime changes require synchronization of
  `ARCHITECTURE.md` and its Chinese translation.

## Security and Evidence Boundaries

- The Dungeon Maintainer bridge remains development-only, localhost-only, and
  opt-in. Production code must not expose its global bridge.
- External tools may receive only the documented player-visible projection.
  Never expose hidden answers, unrevealed hints, full maps, saves, inventory,
  identity, hidden judge details, credentials, private endpoints, or complete
  snapshots.
- SQL is entered through the fixed visible player textarea and executed inside
  the browser. A tool must not accept hidden SQL parameters or receive an
  administrator answer. The only SQL exception is text already visible in the
  currently open player textarea, within the projection documented by
  `ARCHITECTURE.md`.
- Preserve deterministic grading, progression, migrations, and authored-content
  identity. A compatibility or version change needs explicit scope and focused
  migration evidence.
- Do not add third-party art, fonts, audio, copied level text, or runtime
  dependencies without license, attribution, bundle, and security review.

## Validation and Stop Conditions

- Run focused tests first, then the applicable architecture check, full game
  tests, and build in proportion to the change.
- Review the complete Diff for scope drift, stale facts, generated artifacts,
  security exposure, and unverified behavior.
- Stop and request direction when requirements materially conflict, approval no
  longer matches scope, a safety boundary would be weakened, or required
  evidence cannot be obtained without broader authority.
